# 容量规划与限流

这一页讲怎样设置引擎的并发参数：槽位、单用户限额、模型连接的并发名额和运行时长上限，以及调大调小各有什么后果。测出来的容量数字见[性能基准](/zh/benchmarks/)，调度机制见[执行模型](/zh/engine/execution)。

## 四个参数

槽位和模型并发是两个独立的上限，另外两个是单用户限额与时长：

| 参数 | 控制什么 | 默认 |
|---|---|---|
| `host.Config.Slots` | 这个进程同时运行的会话数 | 32 |
| `host.Config.UserSlots` | 一个用户最多占几个槽位 | 等于 `Slots` |
| `llm` 客户端的 `calls` | 一条连接同时在途的模型请求数 | 4 |
| `host.Config.RunLimit` | 一次占用槽位的最长时间 | 4 小时 |

`Slots`、`UserSlots`、`RunLimit` 填 0 时 `host.New` 换成默认值，负数不纠正（见 [Config 参考](/zh/integrate/config#host-config)）；`calls` 是 `llm.NewOpenAI`、`llm.NewAnthropic`、`llm.NewGemini` 的第三个参数，填 0 或负数时用 4。

槽位只在进程内存里：调度器从 feed 得知哪个会话变得可运行，从库里按顺序取出等得最久的，在总槽位和每用户槽位以内交给运行器。一个会话占着槽位时，要么在调用模型（占一个模型名额），要么在执行工具（不占名额），要么在两者之间读写库。名额满时，模型调用在名额上排队，这个会话仍占着槽位。所以 `Slots` 比 `calls` 大出来的部分，只对正在跑工具的会话有用；工具都很快时，把 `Slots` 调到远大于 `calls` 不会提高吞吐，只会让更多会话一边排队一边占着槽位。

在等审批、等用户回答、等子 agent 汇报的轮次不占槽位，也不计入 `UserSlots`。`RunLimit` 也不算这段时间：它按每次进槽位计时，回到槽位重新计。

取会话的顺序：用户自己的会话排在子 agent 的会话前面，同类之间按变成可运行的先后。定时任务的轮次和用户发的轮次一样排队，没有降级。

## 调大调小的后果

| 参数 | 调大 | 调小 |
|---|---|---|
| `Slots` | 更多会话同时在跑：每个多一个 goroutine 和它的内存，库的读写也更多。库只有一条连接，所有读写在它上面排队，1536 个会话以上一轮慢在等这条连接（见[容量](/zh/benchmarks/#容量)）。模型名额不跟着加时，多出的会话只是在名额上排队 | 可运行的会话在库里等槽位，用户感到"发了消息迟迟不开始"。跑长工具的会话会把槽位占满，其他会话全部等待 |
| `UserSlots` | 一个用户的会话能占更多槽位；等于 `Slots` 时，一个发散出很多子 agent 的用户能占满整个分片 | 同一个用户的会话互相排队。子 agent 的会话和父会话算同一个用户，发散多的用户受影响最大。超额的会话留着等，不失败 |
| `calls` | 在途的模型请求更多。超过服务商给账户的并发配额时 429 变多，请求进入重试（见下一节），重试期间名额和槽位都不释放 | 模型请求在名额上排队，会话占着槽位等。名额比服务商配额小时，配额用不满 |
| `RunLimit` | 卡住的运行占着槽位更久才被判失败。一个不回应的模型请求只受每次尝试 3 分钟无响应的限制，一个卡住的工具调用最长占到 `RunLimit` | 正常的长任务也会被判失败，原因是 `the turn reached its time limit of ...` |

几点补充：

- 一条连接只给一个模型用（`host.New` 检查），所以 `calls` 实际是"这个模型同时在途的请求数"。可以给同名模型再建一条连接（如 `openai-2`）并带自己的配额，但它在 `Models` 里是另一个可选模型：一轮用的是它被提交时选定的那条连接，引擎不会在两条连接之间分摊。
- 配了 `ClientFor` 时，每个用户的请求走这个函数返回的客户端，名额按那个客户端算；`ClientFor` 每次应返回同一个客户端，否则名额形同虚设。分片里同时在途的请求最多是"用户数 × 每用户客户端的 `calls`"，再受 `Slots` 限制。
- 一个会话最多有 20 轮排在当前轮次后面，再发消息会被拒绝（`ErrQueueFull`）。这不是全局的队列上限：可运行的会话数没有上限，只是在库里等槽位。

## 怎样选值

先定 `calls`：它对应服务商给这个账户（或这个用户的密钥）的并发配额，不要超过它。突发请求在名额上排队，不会打爆配额。

再定 `Slots`。从机制推出的起点是：所有连接的 `calls` 之和，加上预计同时在跑工具的会话数。这是推断，不是测出来的。长命令可以放到后台：后台调用不占槽位，在自己的队列里跑，见[后台调用](/zh/benchmarks/#后台调用)。

`UserSlots` 按"一个用户最多该用掉分片的几分之一"来定。不设时，一个让 1024 个会话忙着的用户会占满 512 个槽位，其他用户的轮次 p50 要等 206 s；设为 64 后只等 8 ms（[多用户](/zh/benchmarks/#多用户)）。用户会大量使用子 agent 时，要给他留出父会话加子 agent 的余量；父会话等子 agent 时会让出槽位，所以不必按"父加子"成倍预留。

`RunLimit` 设成最长的正常任务再留余量。它同时也是一个卡住的工具调用最长能占多久，所以不宜远大于需要。

现有基准里和这几个参数有关的结果（v0.18.0，模拟模型每次 5 秒 ± 2 秒、工具每次 1 秒，Apple M1 8 核 8 GB，单个 SQLite 库，各测一次；全部数字见[性能基准](/zh/benchmarks/)）：

| 实验 | 设置 | 结果 |
|---|---|---|
| `steady` | 512 到 4096 个活跃会话，`slots` 和 `calls` 都等于会话数 | 1536 个会话时一轮比单独运行慢 5%；4096 个时是 2.8 倍，多出的时间几乎都在等 SQLite 连接 |
| `burst` | 一次提交 3000 轮，`slots` 512，`calls` 256 | 在途请求始终不超过配额，没有 429，总时长是理论下限的 1.04 倍 |
| `background` | 256 个轮次各跑一个 30 秒的命令，`slots` 32 | 命令放在后台时新会话等 10 ms；留在轮次里时等 144 秒 |
| `users` | 33 个用户共用 512 个槽位，其中一个让 1024 个会话忙着 | 不设 `UserSlots` 时其他用户等 206 秒；设为 64 时等 8 ms |
| `fanout` | 64 轮各发出 8 个子 agent，共 512 个，`slots` 32 | 576 轮全部完成，总时长是理论下限的 1.19 倍；等子 agent 的父轮次都让出了槽位 |
| `mix` | 256 个会话持续发消息，运行中途 1000 个定时任务同时到期，`slots` 512，`calls` 256 | 高峰之外，一轮等到第一次模型请求的 p50 8 ms、p99 3.2 秒；高峰 56.9 秒排空 |

单个分片在这台机器上约 1536 个活跃会话开始变慢，先到的上限是数据库连接，不是 CPU 或内存。多分片的扩展还没有测。要更多容量时，靠加分片，见[多用户与分片部署](/zh/integrate/deploy)。

## 重试会占着槽位

被 429、5xx 拒绝或中途断开的模型请求由客户端重试，最多 8 次（`pkg/llm/connection.go` 的 `retries`）。OpenAI 和 Anthropic 客户端用各自 SDK 的重试：退避从 0.5 秒翻倍到最多 8 秒，带随机抖动，服务商给出不到一分钟的 `Retry-After` 时照它等；Gemini 客户端最多尝试 9 次，退避同样从 0.5 秒到 8 秒。重试期间：

- 这个会话一直占着槽位，模型名额也不释放，所以在途请求数始终不超过 `calls`。
- 用户看到的是这一轮变慢，不是失败。重试都失败时这一轮才失败，原因里带 HTTP 状态码，如 `run: model call: model request failed (HTTP 429); check the selected connection and model`。

每次尝试在服务商 3 分钟没有发回任何字节时放弃（`pkg/llm/idle.go`）。除此之外，一次模型请求没有别的超时，整轮受 `RunLimit` 约束。重试和名额的机制见[模型接入](/zh/engine/models)。

## 判断哪个上限在卡

引擎没有指标接口，也不写日志，能用的是库里的状态、feed 和宿主自己包在模型连接外的计时（怎样做见[运维](/zh/integrate/operations#监控)）。

| 想知道 | 看哪里 | 说明 |
|---|---|---|
| 槽位是否满了 | 库里 `threads.runnable_since` 非空的会话数持续大于 `Slots` | 可运行的会话包括在槽位里跑的和等槽位的。按 `user_id` 分组：集中在少数用户、且这些用户的数目超过 `UserSlots`，是单用户限额在卡；分布在很多用户，是 `Slots` 在卡 |
| 会话等槽位等了多久 | 按 `runnable_since` 排序，看最早的那个离现在多久 | 调度器正是按这个顺序取，最早的那个持续变老就是槽位不够 |
| 模型名额或服务商是否在卡 | 包在连接外的 `Chat` 计时，和服务商报的 token 数一起看 | 内置客户端先排队拿名额再发请求，失败时重试，计时包括这三段。token 数差不多而耗时明显变长，是在排队或重试；分不出是哪一种时，看服务商侧的 429 统计 |
| 重试是否用完了 | feed 上的 `conversation.ModelFailed` 条目，失败轮次原因里的 `HTTP 429` | 重试用完才会有 |
| `RunLimit` 是否太小 | 失败轮次的原因是 `the turn reached its time limit of ...` | 查询见[运维](/zh/integrate/operations#监控) |

::: info 演进
v0.16.0 之前调度状态在 `turns.status` 里（`ready` 就是等槽位），判断要靠 `turn started`、`run ended`、`model call` 等日志。`3c3ed62` 让调度器只从 feed 得知可运行的会话，状态从日志折叠出来，会话变成可运行的时刻记在 `threads.runnable_since`；`34d96a9` 去掉了日志。
:::
