# 水在青天云在瓶：agent 的身首错位现象

2026 年 11 月 8 日 · [English](/articles/head-in-the-cloud)

## 引子

Anthropic 不向中国大陆提供服务。2025 年 9 月，它又禁止了由中国实体控制的公司使用 Claude，不论公司注册在哪里。

想用 Claude Code 的国内开发者于是想了个办法：在海外租一台云服务器，把 Claude Code 装在上面，这样就能访问模型了。但代码、文件和浏览器都在自己的电脑上，于是他们又用内网穿透，把自己的电脑接回那台海外服务器。

最后的结果是：agent 的运行时在大洋彼岸，执行环境在自己的书桌上，中间只有一条用户自己搭的隧道。

![运行时在海外，执行环境在自己的书桌上](/figures/head-in-the-cloud/fig-1-intro.zh.svg)

唐代李翱有一句诗："云在青天水在瓶。"意思是万物各在其位。这里的 agent 正好反过来：每个部分都不在它"应该"在的地方。

这听起来像是特殊环境逼出来的权宜之计，其实不是。Manus 让云端的 agent 操作用户自己的浏览器，结构和这一模一样。Anthropic 自己的 Cowork 也做过类似的调整：最初把整个 agent 放进虚拟机，后来把 agent 循环移了出来。agent 的各个部分对运行位置的要求本来就不同，"身首错位"是常态，不是例外。

本文先拆分 agent 的组成部分，再归纳常见的部署形态，然后分析决定部署位置的因素，并单独讨论中国大陆的情况。最后给出结论：什么场景适合什么形态，每种形态换来了什么。

## 一、agent 由哪几部分组成

通常把 agent 分为三层。

**接入层**：用户与 agent 交互的界面，包括桌面应用、网页、手机 app、终端，以及 Telegram、WhatsApp、Slack、微信、飞书、钉钉等聊天软件中的机器人。

**运行时（runtime）与编排层**：agent 循环本身。它负责组装上下文、调用模型、解析工具调用、做权限判断和审批、调度子任务，以及处理重试和中断。下文简称"运行时"。

**执行环境**：工具实际运行的地方，包括 shell、文件系统、浏览器、桌面应用、数据库和内网服务。它可以是用户的电脑，也可以是本地容器、虚拟机、操作系统级沙箱，或者云端沙箱。

讨论部署时，还需要单独考虑另外两部分。

**模型服务**。除非使用本地模型，它总在远端。因此不存在完全本地的 agent：所有被读入上下文的内容都会发送给模型服务。"本地执行"的准确含义是原始资源留在本地，只有被读取的部分会离开。

**会话状态**，包括对话记录、待执行任务、审批记录和记忆。状态存放在哪里，决定了断线、换设备或进程崩溃之后，谁能继续这个会话。例如 Claude Code 的 Remote Control 功能可以用手机控制本机终端中的会话：执行始终在本机，但连接期间对话记录会保存在 Anthropic 的服务器上，手机端正是依靠这份记录工作的。

## 二、常见的部署形态

图 3 按各部分的部署位置分类，而不是按产品类别分类。同一个产品可能支持多种形态。

![九种部署形态](/figures/head-in-the-cloud/fig-3-forms.zh.svg)

下面说明其中几种。

**形态 2 和形态 3 的区别。** 两者都使用了隔离，但隔离的范围不同（对比见图 5）。形态 2 把运行时和执行环境放在一起隔离，API 密钥、审批逻辑和会话状态因此与模型生成的代码处在同一环境中。一旦模型被注入恶意指令（提示注入），它能执行命令，也就能读取密钥。形态 3 只隔离执行环境，运行时在隔离区外，持有凭证和审批权。

形态 3 的安全性有一个前提：决定"是否越过隔离边界"的逻辑，不能被不可信的输入左右。Anthropic 在一篇介绍隔离设计的工程文章中承认，在 Claude Code 中，沙箱外的特权进程逐条决定命令是否进入沙箱；一段有说服力的注入内容，或用户疲劳时的一次误点确认，都可能让一条命令绕过沙箱执行。

**形态 5：运行时在云端，执行在本地。** 这种形态的出现，是因为有些资源无法复制到云端。代码仓库可以克隆，但登录状态、两步验证、本机 IP、VPN 后的内网、只安装在用户电脑上的软件都无法复制。Manus 本身有云端浏览器，后来又推出了 Browser Operator 扩展，用于操作用户自己的浏览器。官方建议在用户已登录的网站上使用它，其他任务仍使用云端浏览器。

**形态 6：用户自建的常开节点。** OpenClaw 是一个自托管的网关，可以把 WhatsApp、Telegram、iMessage、Slack 等二十多个聊天渠道连接到用户自己设备上的 agent 会话。官方推荐部署在 Mac mini 或 VPS 等常开设备上。这反映了两个需求：运行时需要一直在线，执行环境需要访问用户自己的文件和账号。Claude Code Remote Control 采用同样的结构：本机会话只发起出站 HTTPS 请求，不开放入站端口；向服务端注册后轮询任务；手机和网页只是这个本地会话的客户端。

**形态 8：执行环境往往不止一个。** 同一个 agent 中，文件读写可能直接在宿主机上进行（用户选定的文件夹被挂载进来），shell 命令在虚拟机中运行，需要登录状态的网页在用户的浏览器中打开，计算密集的任务交给云端沙箱。不同工具依赖的资源不同，所以执行环境应按多个来设计。

**形态 9：会话迁移。** Claude Code 可以用 `claude --teleport` 把网页版中的云端会话拉回本地终端继续，桌面应用也能把本地会话交给云端继续。运行时在本地和云端之间换了位置，会话本身没有中断。

## 三、决定部署位置的因素

我把影响部署位置的因素归纳为七个。每个因素主要作用于某一部分或某一条边界，各部分因此被分开部署。

![每个因素只拉动一部分，各部分因此被分开](/figures/head-in-the-cloud/fig-4-forces.zh.svg)

### 1. 资源位置：执行环境要靠近资源

agent 操作的资源在哪里，执行环境就需要在哪里。关键在于资源能否复制。

可复制的资源，如代码仓库、公开数据和依赖包，可以搬到云端。所以编码 agent 最先实现了云端托管：克隆仓库，在云端执行，最后提交 PR。

不可复制的资源，如登录状态、设备身份、内网访问权限、本地软件、外接硬件，以及用户不愿上传的大量私人文件，会把执行环境留在本地。形态 5 和形态 6 都由此产生。

### 2. 在线时长：运行时要部署在常开的地方

agent 任务越来越长，可能持续数小时，中途还要等待人工审批。用户设备却不是一直在线的：笔记本会合盖，手机会在后台终止进程。

只要任务时长超过设备的在线时长，运行时就需要部署在常开的地方，可以是厂商的云（形态 4），也可以是用户自己的常开设备（形态 6）。

### 3. 安全隔离：凭证和审批权不应与执行环境放在一起

模型输出不可信，执行环境需要隔离，这已是共识。进一步的问题是：哪些东西不应与执行环境放在一起？答案是凭证和审批权。

Anthropic 介绍 Claude Code 网页版时写道，git 凭证、签名密钥等敏感凭证永远不进入沙箱。沙箱中的 git 客户端只持有一个范围受限的凭证，用它访问一个代理服务；代理检查分支名和目标仓库，再代为执行真正的操作。Cowork 的做法类似：凭证保存在宿主机的钥匙串中，虚拟机只获得一个按会话签发、权限收窄、可单独吊销的令牌。

这一因素推动运行时与执行环境分离，是形态 2 转向形态 3 的主要原因。

### 4. 故障隔离：执行环境出错时，运行时应能继续工作

Cowork 的一次架构调整很好地说明了这一点。

Cowork 是一个桌面 agent。最初，整个 agent 都运行在本地虚拟机里，包括 agent 循环和代码执行，属于形态 2。后来，团队把 agent 循环移到了宿主机上，只把代码执行留在虚拟机里，变成了形态 3。Anthropic 给出的原因是：虚拟机一旦启动失败，整个产品就无法使用；循环放在外面以后，虚拟机出故障时 agent 仍然可以回复用户、协助排查。同一时期，本地 MCP 服务器也移出了虚拟机，因为放在里面难以审计，虚拟机升级时依赖容易出问题，而且有些 MCP 需要访问本机的数据库等进程，本来就只能运行在宿主机上。调整之后安全性基本不变，因为代码仍在虚拟机里执行。

![Cowork 把 agent 循环移出了虚拟机](/figures/head-in-the-cloud/fig-5-cowork.zh.svg)

如果运行时和执行环境在同一个故障域（一处出错会一起失效的范围）中，执行环境的故障就是整个 agent 的故障：虚拟机无法启动、容器内存溢出、沙箱服务超时，用户看到的都是一个没有响应的界面。分开之后，执行环境的故障只是一次失败的工具调用。运行时仍可告知用户、重试、切换执行环境，或请求用户协助。

由此得出一条设计原则：执行环境的故障应当是运行时能够处理的事件，而不应导致运行时本身失效。

### 5. 闲置成本：agent 的大部分时间在等待

一个 agent 会话的大部分时间是空闲的：等待模型返回、等待工具完成，更多时候是等待用户回来。如果为每个会话分配一个常驻容器，大部分算力都浪费在等待上。

这一因素在云端最明显。它让各部分采用不同的生命周期：运行时做成无状态、多租户共享的服务，状态存入数据库，由空闲的进程接手；执行环境按需创建，可以休眠和从快照恢复；接入层可以随时断开重连。如果把三者绑在一起，就得按其中寿命最长的那个付费。

### 6. 接入与身份：接入层要在用户已经在用的地方

接入层只取决于用户在哪里。

手机是用户最常用的设备，却最不适合做执行环境：系统限制严格，后台运行受限，也没有通用的文件系统。聊天软件已经安装好，支持推送，在企业场景中还自带身份和组织架构信息。所以接入层通常最先与其他部分分离。分离之后，审批也随之改变：从同步的弹窗变为异步的消息。agent 暂停执行，用户在手机上收到通知并确认，agent 再继续。

### 7. 网络可达性与合规：运行时必须能访问到模型和工具

运行时需要同时访问模型服务和执行环境。如果某个模型只能在特定网络或特定地区访问，运行时就只能部署在那里，即使资源和用户都在别处。引子中的海外服务器方案就是这样形成的，企业内网中的模型服务也是同样的道理。

合规要求的作用方向相反：数据不能离开某个范围，就把包括模型在内的所有部分都部署在这个范围之内。

### 补充：商业控制

部署形态也不完全由技术决定。运行时部署在云端，厂商就能掌握计费、模型路由、数据和跨设备体验，这对商业模式有利。开源和自托管项目则倾向于把运行时留给用户。分析一个产品的形态时可以考虑这一点，但它不能替代前面那些技术约束。

## 四、中国大陆的情况

中国大陆并没有产生全新的部署形态。不同的是各因素的权重：网络可达性和合规要求的影响远大于其他地区。因此，同一个软件在国内常常被部署成与设计初衷不同的形态，见图 6。

![同一个软件，在国内常被部署成另一种形态](/figures/head-in-the-cloud/fig-6-china.zh.svg)

### 1. 运行时在海外，执行在本机

引子中的方案，从结构上看就是形态 5，但成因不同。Manus 等产品采用形态 5，是因为资源无法复制到云端，而厂商希望运行时留在云端。海外服务器方案中，运行时被迫部署在海外，是因为只有那里能访问模型服务；执行环境必须留在本地，是因为用户的资源在本地。

值得注意的是，用户在没有任何厂商支持的情况下，自己把运行时和执行环境拆开了。这说明这两部分之间的边界是真实存在的，并不是某个产品的设计偏好。

这种做法的代价也很明显。第一，海外服务器同时持有模型账号凭证和一条通往用户个人电脑的连接；服务器一旦被入侵，攻击者就能直接操作用户的电脑，这正是"凭证和审批权不应与执行环境放在一起"的反面。第二，每次工具调用都要跨境往返，延迟和稳定性都受影响。第三，这种使用方式违反了服务提供方的地区政策，账号随时可能被封禁。

企业层面也有类似情况。据英国《金融时报》2026 年 7 月的报道，一些中国企业通过新加坡等地的海外实体、云服务商转售的接口等途径使用 Claude；Anthropic 则通过检测电脑时区等信号、打击转发请求的"中转站"来封堵。

### 2. 聊天软件即身份系统

飞书、钉钉、企业微信都提供官方的机器人和应用接口。agent 接入后，可以直接获得用户的身份、所属部门和文档权限。这些信息由 IM 平台维护，agent 不必另建一套身份系统。对企业来说，这往往比 agent 本身更难替代。

个人微信过去没有面向个人账号的官方机器人接口，社区方案大多依赖模拟协议或客户端注入，有被封号的风险。2026 年 3 月，腾讯推出了微信 ClawBot 插件，用户在运行 OpenClaw 的设备上执行一条安装命令、扫码之后，就可以在微信中与自己的 agent 对话（插件最初以灰度方式推出）。国内用户最多的聊天软件，正式成为了自托管 agent 的一种官方接入层。运行时的位置没有变化，仍在用户部署 OpenClaw 的设备上。

### 3. 本地优先的软件被部署到云上

OpenClaw 的设计是本地优先，官方推荐部署在用户自己的常开设备上（形态 6）。2026 年初它在国内流行之后，阿里云、腾讯云、华为云等主要云厂商都推出了预装 OpenClaw 的轻量服务器镜像，可以一键部署，再接入飞书、钉钉、企业微信或 QQ。火山引擎还推出了与飞书深度集成的托管版本。

于是在国内，很多 OpenClaw 实例的运行时和执行环境都在云服务器上，接入层在国内 IM 中，实际上变成了形态 7。

有两个细节值得注意。第一，部署教程会根据要访问的服务选择服务器地域：接国内 IM 建议选国内地域，部分教程则建议选海外地域。这正是网络可达性在决定运行时的位置。第二，部分一键部署流程会直接向公网开放 SSH 端口和网关端口。原本运行在家庭网络中的网关，到了云上就直接暴露在公网中，安全要求随之改变。

### 4. 保留运行时，替换模型

另一种常见做法是保留 Claude Code 等 agent 的运行时，把模型换成国产模型。智谱 GLM、Kimi、DeepSeek、MiniMax、通义千问等都提供了兼容 Anthropic 接口格式的服务，用户修改接口地址和密钥即可切换。

这说明运行时和模型服务也可以独立替换。一个设计良好的 agent 运行时，正在成为一种通用的客户端，可以连接不同厂商的模型。

与此相关的还有第三方"API 中转"服务，它们转售海外模型的接口。这种情况下，中转方能看到完整的上下文，包括代码、文件内容和用户粘贴进来的密钥。模型服务放在哪里、由谁运营，本身就是安全边界的一部分。

### 5. 私有化部署：所有部分都在企业内网

在企业市场，方向正好相反。出于数据安全和数据出境方面的监管要求，以及信创（信息技术应用创新，即国产化替代）的需要，很多企业要求私有化部署：接入层、运行时、执行环境和模型都部署在企业内网中，模型使用可本地部署的国产开源模型。

这是合规因素压过其他所有因素的结果。它和全球范围内运行时向云端集中的趋势相反，但遵循的是同一套逻辑。

### 小结

部署形态是由各因素的权重决定的。权重变了，同一个软件就会落在不同的形态上（图 6）。

## 五、分开部署之后的工程问题

各部分分开部署之后，原本的函数调用就变成了跨进程、跨机器甚至跨信任域的通信。每一条边界都会带来新的工程问题。

### 接入层与运行时之间：会话协议

接入层可以随时断开，因此会话协议必须支持断线续传和多端同步：手机和桌面看到的应是同一个会话的同一个状态。这要求状态由运行时持有并持久化，客户端只负责展示。审批也必须是可持久化、可异步处理的对象，不能依赖某个连接上的回调，因为审批者可能在几小时后、在另一台设备上才处理。

### 运行时与执行环境之间：远程调用的语义

本地函数调用不会丢失，远程调用会。超时之后，运行时无法确定对方是否已经执行。对 `ls` 这样的命令无关紧要，对付款或 `git push` 就很关键。运行时因此需要区分"未执行"和"可能已执行"，并明确哪些工具可以安全重试。

文件同步是最复杂的部分：采用挂载、同步还是复制？哪一份是权威副本？冲突如何处理？Cowork 把用户选定的文件夹挂载进虚拟机，提供只读、读写、读写但不可删除三种模式。挂载也有陷阱：必须先解析符号链接再校验路径，否则授权文件夹中的一个符号链接就能指向外部。

执行环境的生命周期也会计入延迟。沙箱冷启动需要数秒，从快照恢复可能更快也可能更慢，这些都会直接影响用户等待 agent 第一个动作的时间。

### 运行时在云端、执行在本地：控制方向反转

通常是本地程序调用云端服务。在形态 5 中则相反，由云端向用户的电脑发出指令。

![运行时在云端时，最终的权限检查要放在本地](/figures/head-in-the-cloud/fig-7-reverse.zh.svg)

连接通常由本地主动发起，再轮询或保持长连接，所以不需要开放入站端口，设备没有公网地址也能连通。Remote Control 和各类浏览器扩展都采用这种方式。它解决了网络连通问题，但没有解决信任问题。

关键在于权限检查由谁执行。如果审批和策略只在云端运行时中执行，本地就会无条件执行云端发来的所有指令；云端运行时一旦被注入恶意指令，本地设备就完全暴露。安全公司 Mindgard 分析 Manus 的浏览器扩展时指出，该扩展可以读写 cookie 和 local storage，而用户的授权在整个对话期间持续有效。

结论是：当运行时与执行环境属于不同的信任域时，最终的权限检查必须在执行环境一侧完成。执行环境需要能够自行拒绝，而不能仅依赖运行时已经检查过。

引子中的海外服务器方案同样适用这条结论，而且风险更高，因为那条连接是用户自己搭建的，通常没有经过任何安全设计。

### 凭证：放在不执行不可信代码的一侧

每增加一条边界，都需要重新确认凭证放在哪一侧。目前较好的做法是：真实凭证留在不执行不可信代码的一侧，执行环境只获得范围受限、可吊销的令牌，由边界上的代理完成实际操作。

Cowork 还在虚拟机内设置了一个代理，拦截发往 Anthropic API 的请求，只放行携带本虚拟机会话令牌的请求。它防范的是这样一种攻击：工作区中的恶意文件附带攻击者的 API 密钥，诱导 agent 把数据发送到 Anthropic API。由于这个地址本来就在出站白名单中，普通的网络限制拦不住这种请求。

### 可观测性：隔离也会挡住安全软件

Cowork 推出后，企业安全团队提出了一个问题：为什么终端安全软件（EDR，终端检测与响应）看不到虚拟机内部？原因是，用来隔离 Claude 的虚拟机，同样把宿主机上的安全软件隔离在外。在 EDR 看来，Cowork 只是一个无法查看内部的虚拟机进程。

因此，每增加一层隔离，都需要重新设计可观测性。隔离越彻底，agent 就越需要主动报告自己的行为。

## 六、什么场景用什么形态

前面分析了形态是怎么来的。这一节直接给出判断。先用图 8 的四个问题选出形态，再看下表中每种形态换来了什么、付出了什么。

![四个问题，选出部署形态](/figures/head-in-the-cloud/fig-8-decide.zh.svg)

| 场景 | 选这个形态 | 换来的 | 付出的 |
|---|---|---|---|
| 开发者在自己电脑前，处理本地仓库 | 1 全本地 | 零部署，零额外延迟，所有本地资源直接可用 | 设备离线任务就停；安全依赖逐条审批 |
| 想让 agent 自动运行，不想逐条审批 | 3 本地运行时 + 隔离执行 | 自动化程度高，凭证不进隔离区，执行环境出错 agent 仍可响应 | 要维护一条隔离边界和文件挂载 |
| 一次性实验，环境里没有任何凭证 | 2 整体隔离 | 实现最简单，用完即弃 | 不适合长期使用，环境里一旦有凭证就有泄露风险 |
| 仓库可克隆，要并行跑多个长任务，结果是 PR | 4 云端托管 | 可并行，关掉电脑任务照样继续 | 访问不到本地资源；数据和计费由厂商掌握 |
| 必须使用用户的登录状态，如后台系统、需要登录的网站 | 5 云端运行时 + 本地执行 | 能使用无法复制的资源 | 本地设备必须在线；权限检查必须放在本地 |
| 个人助理，随时用聊天软件派任务，操作自己的文件和账号 | 6 远程接入 + 本地运行时 | 常开，能访问本地资源，不用安装新 app | 要自己维护一台设备；每条聊天消息都会成为 agent 的输入 |
| 企业员工助手 | 7 企业 IM 接入 + 云端 | 身份、组织架构和权限现成可用 | 能力受 IM 平台接口限制 |
| 金融、政务、医疗等强监管行业 | 全部署在内网的私有化方案 | 满足合规要求 | 模型能力受限，运维成本高 |
| 面向普通用户的通用桌面助手 | 3 + 8 | 安全与本地资源兼顾，不同工具各用合适的执行环境 | 系统最复杂，可观测性要重新设计 |
| 所需模型在当地无法访问 | 不建议采用海外服务器方案；改为保留运行时、替换模型 | 合规，连接稳定，没有封号风险 | 需要接受另一家模型的能力差异 |

这张表可以归结为三句话。

**资源决定执行环境的位置。** 资源能复制，就上云；不能复制，执行环境就留在资源所在的地方。

**在线时长决定运行时的位置。** 任务比设备在线时间长，运行时就放到常开的地方；否则留在本地最简单。

**信任边界决定权限检查的位置。** 运行时和执行环境分属不同信任域时，权限检查放在执行环境一侧；凭证始终留在不执行不可信代码的一侧。


## 七、结论

**部署形态不会统一，但各部分之间的接口会逐步标准化。** 影响部署的因素会长期存在：有的资源可以复制，有的不能；有的设备常开，有的不是；模型输出永远不可信；各地的网络和监管条件也不同。所以上述形态都会继续存在。趋向标准化的是三个接口。运行时与模型之间的接口已经基本标准化，国产模型兼容 Anthropic 接口就是例证。运行时与执行环境之间，正由 MCP 和各家沙箱 API 逐步填补。接入层与运行时之间，即支持断线续传、多端同步和异步审批的会话协议，目前最缺乏标准。

**运行时将与部署位置无关。** 如果运行时本身无状态、所有状态都持久化，它就可以运行在笔记本、Mac mini、海外服务器或云端集群上，代码无需修改。

**执行环境将成为可按需连接的资源。** 一个会话可以同时连接多个执行环境，可以在中途更换，执行环境的故障只是一个可处理的事件。

**对构建 agent 基础设施的建议：** 从一开始就把各部分实现为独立的进程，通过明确的接口通信，即使它们暂时都运行在同一台机器上。将来需要把某一部分迁移到别处时，边界已经存在。Cowork 能把 agent 循环移出虚拟机，引子中的用户能把运行时搬到海外，都是因为这条边界本来就在。
