# 接下来要测的

[现有结果](/zh/benchmarks/)测于 v0.8.3 到 v0.8.5，只覆盖一个进程、一个 SQLite 分片、一个用户，早于多用户、分片、沙箱接口和 v0.16.0 的日志重建，而且没有一个是用 `bench/run.sh` 测的。这一页列出下一轮要测什么。每个实验先写清楚要回答的问题，这样不论结果如何都算数。

规矩和 `bench/README.md` 一致：除非特别说明，模型和工具都是模拟的；用 `bench/run.sh` 跑，一次只跑一个实验，机器保持空闲，睡过的结果丢掉；原始输出留在 `bench/results/`，开头写着命令、提交、时间和机器，站上的每个数字都能追到那里的文件。

## 每个实验怎么做

**1. 重测。** `bench/run.sh` 不带参数，按 `bench/run.sh -l` 列出的顺序跑全部实验，每个实验的输出带上命令和提交，取代 `results/` 里早于它的文件。要回答的问题包括：每轮的读写次数和磁盘在日志模型下是多少（v0.8.5 是 68 次读、15 次写、约 11.6 KB），停放会话还是不是几乎不占内存，崩溃恢复的新做法（接手会话时把已开始、没有结果的调用记为被切断）是否仍然做到没有工具执行两次。run.sh 每个实验只跑一次、留一份输出；要给数字一个波动范围，得把同一实验多跑几次、分别留下输出。

**2. 变慢的原因。** 对 4096 档做 profile：`steady` 和 `burst` 有 `-cpuprofile`，`soak` 有 `-pprof`；再加上阻塞、互斥锁和 SQLite 忙等时间，并记录每一轮被接纳、发出模型请求、结束的时间点。第一条线索是在途模型请求的峰值：v0.8.5 上 4096 个会话时只有 3774。先看重测之后变慢是否还在。

**3. 租约接管。** run.sh 里的 `crash-lease`（`crash -n 400 -kills 8 -lease 1500ms`）已经会让一个备用进程等在分片上。报告从 kill 到备用进程服务第一轮的间隔，并做和崩溃实验相同的正确性检查：每一轮都完成，没有工具执行两次，被中断的调用都标成"可能已生效"。

**4. 吵闹邻居。** `bench users`（`325792f`）已经实现：一个分片上 32 个用户各用自己的密钥和配额（`host.Config.ClientFor`），旁边一个重度用户占着比他的密钥能服务的更多会话；报告其他用户等到第一次模型请求的时间、一轮耗时、Jain 公平指数，以及按用户分的 429 和失败轮次。run.sh 里有三档：`users`；`users-slots` 加 `-user-slots 64`，用 `host.Config.UserSlots` 限住每个用户的槽位；`users-limit` 再让重度用户的密钥在服务商那里超额（`-heavy-calls 64 -heavy-limit 32`）。

**5. 沙箱命令的开销。** `steady -command`（`325792f`）把每次工具调用换成经 `run_command` 在沙箱里真跑一次 `sleep`。run.sh 里有 `steady-workspace-write` 和 `steady-full-access` 两档，各 1024 个会话，和同规模的 `steady-1024` 对比 p50、p99 与每轮 CPU。

**6. 连接的成本。** `bench conns`（`ce11149`，v0.13.0）用一个个独立进程分别跑分片、路由和客户端，每个用户一条空闲连接，按档位报告分片（和路由）每条连接加的常驻内存、堆、goroutine、文件描述符，以及只有心跳时的 CPU；`-storm` 在最后一档杀掉分片再拉起，按协议的重连规则计时到全部客户端回来。run.sh 里直连测到 8000 条（`conns`），经路由测到 4000 条（`conns-router`），上限来自同一台机器上的文件描述符和临时端口，更多要调高系统上限或换 Linux。

**7. 多分片扩展。** 每个分片一个独立进程、各有自己的数据库，前面是路由。按分片数报告吞吐和 p99，以及路由带来的额外延迟。现在还没有实验。

**8. 长历史。** 先给会话预填 100 轮和 1000 轮历史，再跑容量实验。报告每轮 CPU、常驻内存和 p50。`resume` 已经按 10、100、1000 轮历史计唤醒耗时，容量实验还没有预填历史的选项。

**9. 真实模型抽样。** 用真实服务商跑几十个会话，检验模拟的假设（固定延迟加抖动、没有首字延迟、没有 token 限制）和现实差多远。
