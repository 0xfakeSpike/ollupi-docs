# 接下来要测的

[现有结果](/zh/benchmarks/)只覆盖一个进程、一个 SQLite 分片、一个用户，而且测于多用户、分片和沙箱改动之前。这一页列出第二轮要测什么。每个实验先写清楚要回答的问题，这样不论结果如何都算数。

规矩和第一轮一样：除非特别说明，模型和工具都是模拟的；一次只跑一个实验，机器保持空闲；原始输出留在 `bench/results/`，站上的每个数字都能追到那里的文件。

## 每个实验怎么做

**1. 重测。** 用第一轮同样的命令在当前引擎上跑，每个实验跑三次，让每个数字有波动范围。

**2. 变慢的原因。** 对 4096 档做 profile（CPU、阻塞、互斥锁，以及 SQLite 忙等时间），并记录每一轮被接纳、发出模型请求、结束的时间点。第一条线索是在途模型请求的峰值：4096 个会话时只有 3774。

**3. 租约接管。** `crash -lease` 已经会启动备用进程。报告从 kill 到备用进程服务第一轮的间隔，并做和崩溃实验相同的正确性检查：每一轮都完成，没有工具执行两次，被中断的调用都标成"可能已生效"。

**4. 吵闹邻居。** 一个分片上放两组用户。一组提交量远超自己的槽位份额，或者它的连接持续报错；测另一组的 p50、p99，和没有这组用户时对比。`bench users`（`325792f`，v0.12.1）已经实现：每个用户走自己的密钥和配额（`ClientFor`），另有一个重度用户占着比他的密钥能服务的更多会话；报告其他用户等到第一次模型请求的时间、一轮耗时、Jain 公平指数，以及按用户分的 429 和失败轮次。`-user-slots` 设 `UserSlots`，`-heavy-limit` 让重度用户的密钥在服务商那里超额。`bench/README.md` 写明还没有结果。

同一提交给 `steady` 加了 `-command`：每次工具调用改成经 `run_command` 和沙箱真跑一次 `sleep`，用来测沙箱命令的开销，也还没有结果。

**5. 多分片扩展。** 每个分片一个独立进程、各有自己的数据库，前面是路由。按分片数报告吞吐和 p99，以及路由带来的额外延迟。

**6. 长历史。** 先给会话预填 100 轮和 1000 轮历史，再跑容量实验。报告每轮 CPU、常驻内存和 p50。

**7. 真实模型抽样。** 用真实服务商跑几十个会话，检验模拟的假设（固定延迟加抖动、没有首字延迟、没有 token 限制）和现实差多远。
