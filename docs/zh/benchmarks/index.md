# 性能基准

这一页回答：一个 Ollupi 进程能同时服务多少会话，和 pi、DeepSeek Harness 比怎么样，以及进程被杀、模型报错、长命令、重度用户出现时，它还能不能把活干完。测的是调度和持久化，不是模型质量。

**测量条件**：Ollupi v0.18.0，2026-11-19，Apple M1（8 核，8 GB），一个 SQLite 数据库，每个实验跑一次。引擎是真的（宿主、数据库、调度、网关），只有模型和工具是模拟的：模拟模型经真实的 OpenAI 客户端访问，在途请求超过配额时回 429。除非特别说明，一次模型调用 5 s ± 2 s，一次工具调用 1 s，一轮 3 次模型调用加 2 次工具调用，单独跑 17 s。每个数字都能在引擎仓库的 `bench/results/` 和 `bench/compare/results/` 找到原始输出，方法和命令见 `bench/README.md`。

下一轮要测什么，见[接下来要测的](/zh/benchmarks/plan)。

## 结论

| 问题 | 答案 |
|---|---|
| 和 pi、DeepSeek Harness 比？ | 内存最少；只有它把 3000 个同时提交的轮次全部跑完，也只有它在 `kill -9` 后把后台命令的结果带回会话；1024 个会话以上比 pi 慢 |
| 同时跑多少个会话还不变慢？ | 1536 个时一轮比单独跑慢 5%；4096 个时是单独跑的 2.8 倍，慢在等 SQLite |
| 停放的会话花多少？ | 5 万个停放会话共 34 MB 常驻内存，每个约 7 KB 磁盘 |
| 3000 个轮次同时提交、配额 256？ | 全部完成，没有 429，耗时是配额允许下限的 1.04 倍 |
| 长命令会拖住别的会话吗？ | 放到后台就不会：新会话等 10 ms，命令留在轮次里时要等 144 s |
| `kill -9` 之后剩下什么？ | 每一轮都完成，没有工具执行两次；备用进程 1.3 s 接管 |
| 一个重度用户会拖住其他用户吗？ | 设了单用户槽位上限就不会：其他用户等 8 ms，不设时等 206 s |
| 模型出错、变慢会让轮次失败吗？ | 不会：5% 的请求出错或延迟长尾，都没有轮次失败 |
| 跑久了会变慢吗？ | 不会：8 分钟、约 3.3 万个轮次，一轮耗时和内存都持平 |
| 历史变长要付多少？ | 历史从 8 轮到 55 轮，一轮从 3.6 s 变成 15.7 s，慢在等 SQLite |

## 对比

![四个 harness 在同样负载下的对比](/images/bench-compare.svg)

同一个模拟模型、同一个驱动；Ollupi 作为独立进程运行，驱动经它的协议访问，每 64 个会话属于一个用户、各用一条连接。内存是承载会话的那个进程的 `phys_footprint`。版本：pi-coding-agent 1.5.2、pi-durable 1.5.2、DeepSeek Harness 0.2.2-rc.5。

| | Ollupi | pi (SDK) | pi-durable | DeepSeek Harness |
|---|---|---|---|---|
| 每个停放会话的内存 | 14 KB | 90 KB | 64 KB | 147 KB |
| 2048 个会话同时跑时的内存 | 398 MB | 777 MB | 925 MB | 1371 MB |
| 2048 个会话同时跑时，一轮 p50 比单独跑慢 | 76% | 28% | 58% | 330% |
| 3000 个轮次同时提交、配额 256，完成数 | 3000 | 483 | 527 | 1764 |
| 运行中 `kill -9` | 每一轮都完成，没有工具执行两次 | 进行中的轮次停住 | 每一轮都完成，没有工具执行两次 | 1000 个轮次里 980 个以中断结束 |
| 后台命令运行中 `kill -9` | 200 个结果全部回到会话 | 没有后台调用 | 没有后台调用 | 200 个一个也没回来 |

Ollupi 内存最少，突发时只有它把轮次全部跑完：超出配额的请求在它自己的队列里等，另外三个把请求全部发出去、靠重试硬撞配额，重试用完的轮次就失败了。它的短板是重负载下的延迟：1024 个会话起比 pi 慢，原因是每一步都先写库、都排在那一条 SQLite 连接上（见[容量](#容量)）。停放内存里的 14 KB 主要是在线用户的：每个连着的用户约占 0.56 MB 堆；同样 2000 个会话都归一个用户时每个只有 6.1 KB。全部数字和方法见引擎仓库的 `bench/compare/README.md`。

## 容量

![活跃会话数与一轮耗时](/images/bench-capacity.svg)

闭环：每个会话上一轮结束就发下一轮，各跑 3 轮；槽位（slot）和模型并发都等于会话数。

| 会话数 | 一轮 p50 | p99 | 模型调用/s | CPU（核） | 常驻内存 | 每轮等 SQLite |
|---|---|---|---|---|---|---|
| 512 | 17.4 s | 21.6 s | 74 | 0.64 | 129 MB | 0.2 s |
| 1024 | 18.4 s | 24.6 s | 137 | 1.23 | 215 MB | 1.4 s |
| 1536 | 17.8 s | 22.4 s | 215 | 1.64 | 308 MB | 0.8 s |
| 2048 | 21.5 s | 27.1 s | 236 | 1.77 | 368 MB | 4.2 s |
| 3072 | 32.0 s | 43.8 s | 241 | 1.88 | 456 MB | 14.2 s |
| 4096 | 48.2 s | 69.8 s | 216 | 1.84 | 531 MB | 29.8 s |

瓶颈在数据库：存储只开一条 SQLite 连接（`pkg/sqlitedb`），一轮要在上面做 126 次读、44 次写；历史越长越明显，见[长跑](#长跑)。1536 个会话以上，一轮比单独跑多出来的时间几乎全是等这条连接的时间（右图两条线几乎重合）。CPU 用不到 2 核，内存也远没到上限。每个活跃会话约 112 KB（512 到 4096 档常驻内存的斜率），每轮约 14 KB 磁盘。

## 内存

5 万个会话停在等用户上：常驻内存 34 MB（堆 10 MB），数据库 341 MB、每个约 7 KB；进程空闲时每秒 0.1 ms CPU；同进程里跑的轮次耗时 5.10 s（模型延迟 5 s）。对照是每会话一个 Ollupi 进程，也就是 Ollupi 取代的逐 agent 隔离：每个进程 17.7 MB，不算容器开销。

## 突发

3000 个轮次同时提交，512 个槽位，连接和服务商都限 256 个在途请求。超出配额的请求在 Ollupi 自己的队列里等：在途请求峰值正好 256，服务商没有回过 429，没有轮次失败，全部 182.9 s 完成，配额允许的下限是 175.8 s。不限并发的 harness 会把请求全部发出去、靠重试硬撞配额，结果见[对比](#对比)。

## 后台调用

![长命令放在后台与留在轮次里](/images/bench-background.svg)

256 个会话分属 64 个用户，每个跑一轮，轮里有一次 30 s 的工具调用；32 个槽位，两种方式下都是同时最多 32 个命令。每秒来一个新会话，发一个单独跑 5 s 的轮次。命令放在后台时，新会话的第一次模型请求 p50 只等 10 ms，一轮 5.1 s；命令留在轮次里时，长轮次占满 32 个槽位，新会话要等 144 s，一轮 149 s。两种方式下 256 个命令跑完的时间差不多：243 s 和 257 s，每次 32 个的下限是 240 s。

## 恢复

![kill -9 之后的恢复与唤醒](/images/bench-recovery.svg)

500 个会话混着跑工具调用、向用户提问、子 agent 和后台调用（模型 200 ms、工具 300 ms），随机 `kill -9` 30 次：600 个轮次全部完成，没有工具执行两次，被切断的 110 次调用没有一次被重跑；100 个后台调用全部报告回来，其中 58 个报告自己被切断。重启 p50 29 ms。带 1.5 s 租约（lease）、有备用进程等在分片上时 kill 8 次：480 个轮次全部完成，备用进程接管 p50 1.3 s。

1 万个会话在等、500 个在跑时重启：8 ms 就绪，346 ms 内所有在跑轮次的模型请求重新发出。唤醒一个闲置会话：10 轮历史 3.7 ms，100 轮 8.6 ms，1000 轮 89 ms。

## 多用户

![单用户槽位上限](/images/bench-users.svg)

一个分片 512 个槽位，32 个用户各让 8 个会话忙着，另一个用户让 1024 个会话忙着，每个用户用自己的密钥。不设单用户上限时，重度用户占满所有槽位，其他用户的轮次 p50 等 206 s。`UserSlots` 设为 64 后，其他用户只等 8 ms，一轮 17.1 s，和单独跑一样。重度用户的密钥在服务商那里超额时，7,389 个 429 和 148 个失败轮次都只落在他自己身上，其他用户一个 429 都没收到。

## 故障与长尾

1024 个会话，5% 的模型请求回 500，账号上的其他客户端占去最多 256 个配额：没有轮次失败，p99 25.0 s（没有故障时 24.6 s）。1536 个会话，模型延迟对数正态分布（中位数 5 s，σ = 0.6）：没有轮次失败，p50 20.2 s，p99 43.1 s。

## 沙箱里的命令

1024 个会话，每次工具调用经 `run_command` 真跑一次 `sleep 1`，8 核上同时最多 1024 个进程。不进沙箱（完全访问）时一轮 p50 34.1 s；进 macOS 沙箱（工作区可写）时 104.1 s，每轮 563 ms CPU 花在启动沙箱进程上。假工具是 18.4 s。

## 混合负载与子 agent

256 个会话持续发消息，其中 20% 交给子 agent，运行中途 1000 个定时任务同时到期：高峰之外，用户轮次等第一次模型请求 p50 8 ms、p99 3.2 s；高峰 56.9 s 排空；没有轮次失败，各会话一轮耗时的 Jain 公平指数 0.975。64 个轮次各派 8 个子 agent，跑在 32 个槽位上：576 个轮次全部完成，耗时是下限的 1.19 倍，等子 agent 的父轮次都让出了槽位。

## 长跑

![长跑中一轮耗时与内存](/images/bench-soak.svg)

256 个会话连续发 8 分钟，模型 1 s、工具 0.2 s（单独跑 3.4 s）。每个会话跑满 10 轮就换成新会话，每一轮的工作量不变，变的只有时间。32,982 个轮次里，一轮 p50 一直在 3.5 到 3.8 s，常驻内存 100 到 124 MB，goroutine 854 到 1060，WAL 4.1 MB，GC 暂停 p99 不超过 0.16 ms。

`soak-history` 用同样的负载但不换会话，每一轮都比上一轮多带一点历史：历史从 8 轮到 55 轮，一轮 p50 从 3.6 s 变成 15.7 s，其中 12.2 s 在等数据库连接。一轮要重读自己的历史，读写又和其他轮次排在同一条连接上。

## 连接

空闲的客户端连接，一个用户一条。每条给分片加约 50 KB 常驻内存、4 个 goroutine、1 个文件描述符，心跳每秒 0.008 ms CPU；8000 条共 421 MB。经路由时，每条再给路由加 27 到 43 KB、4 个 goroutine、2 个描述符。分片被杀再拉起后，8000 个客户端按协议的规则重连，83 s 全部回来；经路由的 4000 个 44 s。客户端和分片在同一台机器上，测到 8000 条就碰到了系统的描述符和临时端口上限。

## 推不出的

| 想知道的 | 为什么推不出 |
|---|---|
| 真实模型下的容量 | 模拟模型没有首字延迟、按 token 计的排队和服务商的限流窗口 |
| 真实工具的耗时 | 除沙箱命令一项外，工具都是固定时长的假工具 |
| 多分片的扩展 | 所有数字来自一个进程、一个库；分片数加倍时吞吐是否加倍没有测 |
| 波动范围 | 每个实验只跑一次，没有误差范围 |
| 别的机器 | 只在一台 M1 上测过 |

## 复现

在引擎仓库根目录：

```bash
bench/run.sh                     # 依次跑全部 Go 实验，约 2 小时
bench/run.sh -l                  # 列出实验名和命令
bench/run.sh steady-1024 crash   # 只跑这几个
bench/compare/run-all.sh         # 和 pi、DeepSeek Harness 的对比
```

run.sh 一次只跑一个实验；每个实验开始前等到 Docker Desktop 没在运行、机盖开着、CPU 至少 60% 空闲、没有对比实验在跑；期间系统睡过就丢掉结果重跑。结果写到 `bench/results/<实验名>.txt`，开头写着命令、提交、时间和机器。对比实验的准备见 `bench/compare/README.md`。`go test -tags sqlite_fts5 ./bench` 用秒级规模把每个实验跑一遍，检查它要说明的事，不测数字。
