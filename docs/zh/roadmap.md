# 路线图

Ollupi 是一步一步公开做出来的。这一页写清楚哪些已经完成、接下来做什么，以及每一步怎样才算做完。每一项都给出一个能运行或能查看的检验标准；做完之后，结果写进手册或基准页，这一项从这里删掉。

更新于 2026-11-18，对应引擎 v0.17.1、桌面端 0.7.55。

## 现状

| 方面 | 状态 |
|---|---|
| 引擎内核 | 轮次队列、槽位调度、先落库再执行、崩溃恢复，子 agent 和定时任务都是普通会话。v0.16.0（2026-11-17）把调度与持久化的骨架重建为只追加的会话日志：状态从日志折叠出来，变化经 feed 通知调度器、网关和记忆提取，见[设计决策 26](/zh/reference/decisions#_26-以会话日志为中心重建)。v0.17 只做整理，骨架没再动。 |
| 多用户 | 一个 SQLite 文件是一个分片，行带用户，租约让备用进程接管分片，每个用户有自己的槽位上限和模型连接；引擎本身不知道分片，由 `shard` 包把进程当作分片来跑。已实现，还没有测量。 |
| 沙箱 | 本机用 macOS Seatbelt；云沙箱通过 `sandbox.Machine` 接口接入，仓库里还没有这个接口的实现。沙箱限制命令能碰到哪些文件和网络，不限制它用多少内存和 CPU。 |
| 基准 | 九个实验，加上和另外两个 harness 的对照，都在一台机器、一个分片上测，测于 v0.8.3 到 v0.8.5，早于多用户、分片和日志重建；没有一个数字测于当前版本。多用户和连接的实验、按固定规则逐个跑实验的 `bench/run.sh` 都已写好，还没测。见[性能基准](/zh/benchmarks/)。 |
| 评测 | 引擎仓库的 `eval/` 在 Terminal-Bench 2.0 的任务上（经 Harbor、在 Docker 里）用真实模型跑引擎，比较前后两个版本，用来找该改什么、判断改动有没有用。目前只在 10 题的 smoke 子集上跑过，最近一次在 2026-11-09，早于日志重建；没有公开的成绩。 |
| 桌面端 | Apple 芯片的 macOS 应用，2026-10-28 以来发了 58 个版本，作者每天在用；0.7.55 跑在引擎 v0.17.1 上。 |

## 接下来

### 1. 第二轮基准

现有数字早于多用户、分片、沙箱和日志重建，而云服务商最关心的几项主张还完全没有数字。日志重建改变的正是停放成本、每轮读写和每轮 CPU 这几项要测的东西。这一轮重测，并补上这些空白。实验清单和进度见[接下来要测的](/zh/benchmarks/plan)。

做完的标准：首页和基准页上的每个数字都来自 v0.16.0（日志重建）或更新的版本，并且由 `bench/run.sh` 测出；租约接管、吵闹邻居、多分片扩展各有一份公开结果，不论结果好坏。

### 2. 基于执行轨迹的自我改进（RSI）

引擎在每一步执行之前就把它追加进会话的日志：模型输出、推理、工具调用、审批、提问与回答、子 agent 的报告、token 用量。现在这份日志用于崩溃后接着跑、界面上的时间线和长期记忆的提取。下一步是用它来评测 agent，再反过来改进 agent，形成递归的改进循环。

计划分三个阶段，每个阶段单独可用：

1. **轨迹即数据。** 按稳定、有文档的格式导出运行记录，导出前先脱敏，让引擎之外的程序也能读。
2. **评测。** 用改动过的提示词、技能、记忆或模型，回放或重跑记录下来的任务，并给结果打分。分数变差的改动不发布。`eval/` 已经能在 Terminal-Bench 的任务上比较两个版本，但跑的是公开题，还不能重跑从真实使用里录下的任务。
3. **改进循环。** 让 agent 根据自己的轨迹，提出对自身提示词、技能和记忆的修改，只有通过第 2 阶段的才被采纳。

各阶段做完的标准：(1) 导出的轨迹能原样导回；(2) 一次评测能在桌面端录下的真实任务上区分出两版提示词的好坏；(3) 至少一条由 agent 自己提出并被采纳的修改，公开它前后的分数。

### 3. 来自真实使用的可靠性证据

桌面端每天跑的是同一个引擎，这是基准给不了的证据。它会从自己的数据库里，在本机汇总一份不含对话内容的统计：跑了多少轮、失败、中断和恢复的次数、排队等待时间、重试次数。之后按期公开作者自己使用的报告。

做完的标准：应用能导出这份统计，第一份月报发布在本站。

### 4. 可观测性

面向云服务商的框架需要指标，不能只有日志。引擎会通过一个钩子暴露队列长度、槽位占用、每用户等待、租约状态、模型调用重试次数，宿主可以接到自己的指标系统。

做完的标准：基准实验改为从这些钩子读数，不再依赖只在 bench 里的代码。

### 5. 可以跑起来的多用户部署

分片、租约和路由的代码都在，但没有一个读者能照着跑起来的部署，云沙箱也还只有 `sandbox.Machine` 这个接口。参考部署会让读者自己跑起来：一个网关、一个路由、两个分片，再加一个具体的 `sandbox.Machine` 实现（先用容器）。

做完的标准：一条命令启动，多分片基准就在它上面跑。

### 6. 命令的内存和 CPU 限额

槽位限制的是同时运行的会话数，工具池的上限限制的是同时执行的后台工具调用数，模型连接的名额限制的是同时在途的模型请求，三者都不管命令本身。一个占着槽位的会话可以跑一条吃满内存或 CPU 的命令，挤占同一台机器上的其他会话。所以现在只能说"同时跑的会话不超过上限"，还不能说"agent 占用的资源不超过上限"，而后者才是把 agent 放进池子的意义，见[agent 需要一个池子](/zh/intro/why)。

计划让宿主给命令设内存和 CPU 的上限：每条命令一份，再加上一个用户所有命令的总和。超出时结束这条命令，结果作为失败交给模型。限额由 `sandbox.Box` 的实现执行：云沙箱跑在容器里，可以用容器自带的限额；macOS 本机用什么机制还要调研。

做完的标准：一个基准实验让会话跑超出限额的命令，命令被结束、模型收到失败结果，同一分片上其他会话的轮次时长不受影响，公开结果。
