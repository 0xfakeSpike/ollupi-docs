# 路线图

Ollupi 是一步一步公开做出来的。这一页写清楚哪些已经完成、接下来做什么，以及每一步怎样才算做完。每一项都给出一个能运行或能查看的检验标准；做完之后，结果写进手册或基准页，这一项从这里删掉。

更新于 2026-11-08，对应引擎 v0.11.3、桌面端 0.7.24。

## 现状

| 方面 | 状态 |
|---|---|
| 引擎内核 | 轮次队列、槽位调度、先落库再执行、崩溃恢复，子 agent 和定时任务都是普通会话。2026-11-05 以后只改边界，骨架没再动。 |
| 多用户 | 一个 SQLite 文件是一个分片，行带用户，租约让备用进程接管分片，每个用户有自己的槽位上限和模型连接。已实现，还没有测量。 |
| 沙箱 | 本机用 macOS Seatbelt；云沙箱通过 `sandbox.Machine` 接口接入，目前还没有具体的服务商实现。 |
| 基准 | 九个实验，加上和另外两个 harness 的对照，都在一台机器、一个分片上测，早于多用户改动。见[性能基准](/zh/benchmarks/)。 |
| 桌面端 | Apple 芯片的 macOS 应用，2026-10-28 以来发了 28 个版本，作者每天在用。 |

## 接下来

### 1. 第二轮基准

现有数字早于多用户、分片和沙箱的改动，而云服务商最关心的几项主张还完全没有数字。这一轮重测，并补上这些空白。实验清单和进度见[接下来要测的](/zh/benchmarks/plan)。

做完的标准：首页和基准页上的每个数字都来自 v0.11 或更新的版本；租约接管、吵闹邻居、多分片扩展各有一份公开结果，不论结果好坏。

### 2. 基于执行轨迹的自我改进（RSI）

引擎在每一步执行之前就把它写进数据库：模型输出、推理、工具调用、审批、计划、提问与回答、token 用量。现在这份记录用于回放和长期记忆。下一步是用它来评测 agent，再反过来改进 agent，形成递归的改进循环。

计划分三个阶段，每个阶段单独可用：

1. **轨迹即数据。** 按稳定、有文档的格式导出运行记录，导出前先脱敏，让引擎之外的程序也能读。
2. **评测。** 用改动过的提示词、技能、记忆或模型，回放或重跑记录下来的任务，并给结果打分。分数变差的改动不发布。
3. **改进循环。** 让 agent 根据自己的轨迹，提出对自身提示词、技能和记忆的修改，只有通过第 2 阶段的才被采纳。

各阶段做完的标准：(1) 导出的轨迹能原样导回；(2) 一次评测能在桌面端录下的真实任务上区分出两版提示词的好坏；(3) 至少一条由 agent 自己提出并被采纳的修改，公开它前后的分数。

### 3. 来自真实使用的可靠性证据

桌面端每天跑的是同一个引擎，这是基准给不了的证据。它会从自己的数据库和日志里，在本机汇总一份不含对话内容的统计：跑了多少轮、失败、中断和恢复的次数、排队等待时间、重试次数。之后按期公开作者自己使用的报告。

做完的标准：应用能导出这份统计，第一份月报发布在本站。

### 4. 可观测性

面向云服务商的框架需要指标，不能只有日志。引擎会通过一个钩子暴露队列长度、槽位占用、每用户等待、租约状态、模型调用重试次数，宿主可以接到自己的指标系统。

做完的标准：基准实验改为从这些钩子读数，不再依赖只在 bench 里的代码。

### 5. 可以跑起来的多用户部署

分片、租约和每用户沙箱现在还只是接口。参考部署会让读者自己跑起来：一个网关、一个路由、两个分片，再加一个具体的 `sandbox.Machine` 实现（先用容器）。

做完的标准：一条命令启动，多分片基准就在它上面跑。
