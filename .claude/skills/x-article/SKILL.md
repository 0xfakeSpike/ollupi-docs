# X 长文

## 目标

用户要在 X 上成为一个垂直领域（agent 工程）的专家，长期发很多长文。每篇文章的任务只有一个：**把概念和想法讲到人人能懂**。晦涩的文章不发。

这决定了取舍的方向：

- **信誉比单篇流量重要。** 同行被夸大说法冒犯一次，就会点"不感兴趣"或取关，而 X 的排序给负面反馈的扣分远大于点赞的加分（见 `references/x-distribution.md`）。好懂、可信、主题一致，长期看就是流量。
- **读者是聪明的外行。** 默认读者是相邻领域的工程师、产品经理、投资人：聪明，愿意花十分钟，但不知道这个领域的黑话。同行读了不觉得浅，外行读了不觉得难，这才算写对了。
- **好懂不等于浅。** 参考样本 Dan Koe 的长文讲的是控制论和自我发展阶段理论，照样有 2.58 亿浏览和 100 万收藏（2026-11-11 读取）。难懂通常不是题目太深，而是缺了例子、缺了路标、一段塞了太多东西。拆解见 `references/teardown-dan-koe.md`。
- **可读性是最常出的问题。** 用户明确说过，这是目前最严重的问题。审稿时先看"可读性"一节的规则，再看别的。

## 和仓库规矩的关系

这个 skill 管"写什么角度、怎么写得好懂"。`CLAUDE.md` 管站点结构、术语、依据和历史写法，两者冲突时听 `CLAUDE.md`。尤其是：

- 只写有依据的内容；推断要写明是推断。这一条正是这个 skill 要的可信度来源，不要为了好读牺牲它。
- 先写中文，中文定稿、用户确认后再写英文。改动实质内容时先改 `docs/zh/`，停下来等确认。
- 术语全站统一，第一次出现时括号注英文。

## 按任务走

### 写新文章

1. **先调研，再定角度。** 动笔前搜这个话题的最新信息，找出写得最好的几篇（文章、论文、知名博客、X 上的长文），读完后列给用户：每篇的核心观点和思路。然后找出它们都没讲、讲错了或讲浅了的地方，这就是这篇的角度。已经被讲透的观点，正文里一两句话加链接带过，不复述。详见下面"选题和角度"。
2. **定三句话，给用户看：**
   - 一句话结论：读完这篇，读者会相信什么？它和已有文章的结论有什么不同？
   - 读者：谁会读，他们现在怎么想、卡在哪？
   - 带走什么：一张图、一张表、一个判断方法，读者会因为它收藏这篇。

   这三句写不出来，说明还没想清楚，先别动笔。
3. **列大纲。** 每个小标题写成一个论点（完整的句子），只读小标题就能读完整条论证。每节只做一件事。给用户看大纲，确认后再写全文。
4. **写中文全文**，按下面"可读性"和"写法"两节。
5. **用文末的检查清单自查一遍**，把发现的问题和怎么改一起告诉用户。

### 审稿 / 改稿

按检查清单逐项过，可读性的问题优先。除了好不好懂，也要：

- 通读一遍找前后矛盾：前一节说 A、后一节说非 A，结论和正文对不上，同一个东西前后叫法不同。
- 抽查数字和出处是否对得上。
- 看案例是否过时（见"选题和角度"第 4 条），必要时搜一下最新情况。

这类错误一旦被同行指出，比难懂更伤信誉。

每个问题写清：在哪（小标题或段落开头几个字）、为什么读者会卡住、具体怎么改（最好直接给改写后的句子）。按对理解的影响排序，最影响理解的放前面。别列一堆"可以考虑"，挑最重要的五到十处。

用户说"直接改"时才动文件，并且只改 `docs/zh/`。

### 写英文版

从定稿的中文写，不逐句翻译：

- 结构、论点、图、依据保持一致；句子按英文习惯重写。
- 中文里的典故（古诗、庄子）英文读者没有背景，要么用一两句交代清楚它为什么贴切，要么换成英文读者熟悉的对应物，并告诉用户换了什么。中国的产品、公司、节日（淘宝、豆包、双 11）第一次出现时加半句交代。
- 标题按英文读者重新想，同样要说出结论或问题，不要直译。
- 写完对照中文版检查：论点、数字、出处、"这是推断"的标注一个都不能丢。

### 发布配套

文章在推荐流里大约只活 48 小时（排序代码过滤掉 48 小时以前的帖子），所以要准备：

- **发布帖**：一两句说出文章最反直觉的结论，配文章里最能单独看懂的那张图。
- **两三条摘录帖**，在之后几天发：每条一张图加一个论点，能独立成立，结尾指回原文。
- 提醒用户发布后头两个小时亲自回复评论。

细节和依据见 `references/x-distribution.md`。

## 选题和角度

1. **先找已有的好文章，再避开它们的思路。** 动笔前搜最新信息，读这个话题下最好的几篇，然后写别人没写过的东西。复述别人的观点，同行读了没有收获，也不会因此关注你。已有的好文章可以链接，告诉读者"这部分它讲得很好，这篇只补它没讲的"。
2. **要有高屋建瓴的视角。** 不只罗列现象（谁发布了什么、哪家做了什么），要讲清现象背后的结构性变化：什么东西的成本、分工、控制权变了，然后从这个变化往下推，推到商业化（谁会赚钱、谁会受损、钱怎么流）或者对读者的实际影响。现象是例子，结构变化才是论点。
3. **重要的变量织进主线，不另起一节。** 如果某个变量（比如 token 价格）决定了结论，就在论证用到它的地方讲它，让读者看到它怎么推动结论；不要单独开一节"关于 token 价格"，让读者自己去拼。
4. **案例要跟上时间。** 写之前核实每个具体案例的最新状态。某个案例已经过时（产品下线、政策改了、数字被新数据替代），就改讲它代表的趋势，不再把它当作代表例子；需要的话换一个更新的案例。

## 可读性

这是最常出问题的地方，写完和审稿时都先过这一节。

1. **不造词、不造句，用生活中真会说的话。** 不为了显得新颖自创术语或缩略说法，不写读者念出来会觉得别扭的句子。检验方法：这句话你会不会在饭桌上这样跟朋友说？不会，就改成会说的样子。确实需要一个新名字时（比如给几种格局命名），用读者一看就懂的大白话，并且只在第一次出现时解释一次。
2. **一个概念只用一个词，正文和配图一致。** 同一件事换着说法写（"个人 agent""你的助手""本地 AI"），读者会以为是不同的东西。动笔前列一张关键词表，审稿时逐个查：正文、小标题、图里的文字、图注是不是同一个词。
3. **单独拿出来也能看懂。** 任何一句话、一个小标题、一个图标题、一个格局或方案的名字，脱离文章也要好理解。读者在 X 上看到的常常就是一张截图或一句摘录；小标题和图也会被单独转发。不写"它""上述""这三件事"这类要回头找的指代，不用只有读过前文才懂的简称。
4. **大段晦涩的文字，要么改通俗，要么画成图。** 一段话里要同时记住三个以上的东西，或者在讲关系、流程、对比，读者就容易绕晕。先试着改成短句和例子；改不动的，画成图或表。
5. **开头直接给结论，不让引用和背景挡在前面。** 读者在第一屏就要看到结论。典故、名人引语、历史背景、"已有讨论"清单都不能放在结论前面。"已有讨论"或参考清单放到文末，也不要放进提示框（`::: info` 之类）。

## 写法

### 标题

说出结论或问题，让人一眼知道读完能得到什么。用户现有文章常用"典故：直白说明"的标题（如"轮扁斫轮：长期调教的个人 agent 值多少"），冒号后半句必须单独就能看懂。不写"一天改变你的……"这类夸张承诺。

只描述现象的标题是平的。"你的画像，不再只在平台手里"说的是一个现象，看不出写作目的；改成"AI 时代到来，你的用户画像的价值会被谁赚走？"，读者立刻知道这事和自己有关、文章要回答什么。好标题通常带着读者的利害：谁得、谁失、你要付出什么。

标题是问句时，全文要围着这个问题走：第一屏的第一条要点就回答它，各节小标题按问题拆开（谁怎么赚、你能留下多少），结论那一节的标题直接重复这个问题，第一句给短答案。换了标题，就回头按新标题重排结构，不能只改标题那一行。

英文标题不直译，按英文读者重新想；中英两版的问题要是同一个。

### 开头

读者在 X 上先看到标题、封面和开头几行，然后决定点不点开。所以：

1. **第一屏就给结论。** 用几条要点列出全文结论，每条要点单独也能看懂，不用后文才解释的词。
2. **如果要用场景引入，只用一两段，而且是读者熟悉的具体场景**（双 11 比价、约朋友吃饭），场景直接引出结论。典故和引语可以放在结论后面，或者放进正文相关的地方。
3. **交代全文**：分几部分、最后能带走什么。读者知道路有多远，才愿意走。

### 讲一个概念：五步

文章里每个读者可能不懂的概念，都按这个顺序讲：

1. **名字**：白话名称，第一次出现时括号注英文原词。之后全文只用这一个名字。
2. **一句话定义**，定义里不能再出现没解释过的术语。
3. **日常类比**：一个读者每天都碰到的东西。
4. **真实例子**：回到这个领域，最好是 ollupi 或公开产品里真实发生的事，有出处。
5. **边界**：这个概念什么时候不适用，类比在哪里失效。

类比只是入口，讲完类比一定要回到真实机制。只有类比没有机制，同行会觉得浅；只有机制没有类比，外行进不来。

例子（示意）：

> **上下文窗口（context window）** 是模型一次能看到的全部文字。可以把它想成一张办公桌：桌面多大，一次就只能摊开多少文件，新文件放上来，旧的就得收走。agent 跑了几十轮以后，最早的对话会被挤出窗口或压缩成摘要，所以它会"忘记"你一开始交代的事。这个类比也有失效的地方：桌上的文件你都看得见，模型对窗口里靠中间的内容，注意力往往不如开头和结尾。

### 例子要多，而且要具体

抽象的话后面紧跟一个例子。想说明"这是一个通用规律"时，用两三个不同领域的例子，比如 Dan Koe 讲控制论时一口气举了船、恒温器、胰腺三个例子。例子越具体越好：有数字、有产品名、有日期，不写"某公司""某场景"。

### 给读者指路

长文里读者最容易在转折处迷路。在这些地方加一句路标：

- 要举例之前："听起来抽象，看一个例子。"
- 重点之前："下面这句是全文的关键。"
- 深入之前："再往下一层。"
- 节与节之间：一句话说清上一节得出了什么、下一节为什么接着讲这个。

最关键的那句话单独成段。全文七八千字以上时，在中后段读者容易累的地方放一个小结或一张总图。

### 并列的选项

讲几种方案、几种形态、几种格局时，要写清它们具体差在哪里：在哪几个维度上不同、各适合什么情况、选错了会怎样。只列名字加一句描述，读者分不出来。三个以上的选项，用表格对照，列是比较的维度。

### 让读者带走东西

收藏的前提是有用。每篇至少给一样能拿去直接用的东西：检查清单、决策表、"什么情况用什么"的对照、一套步骤。放在文末或单独一节，让人收藏后回来就能找到。

### 结尾

用一个比喻、一张总图或一段短小结，把全篇串成一个整体，让读者带走一张完整的图而不是一堆散点。不要只把开头的要点再抄一遍，也不要硬加"你怎么看？"来刷互动。

### 句子

- 短句，一句话说一件事。一段只讲一个意思，最多两三句。一段里有好几个事实时，拆成短列表，每条一句。
- 主语清楚，少用"这""其"指代上一段的东西。
- 用"你"跟读者说话可以，但不要替读者剖析心理、给读者下判断。
- 不用合称和序号指代："三方""前两份""这三件事""上述两点"单独拿出来没人看得懂，直接写出是谁（"大模型公司、平台和你的个人 agent"）。
- 行业里讨论很多的概念，用大家已经在用的说法，不自己打比方。例如平台让不让第三方 AI 进来，说"开放权限"，不说"开不开门"。
- 读者熟悉的词不用解释（token、API、OpenRouter 这类，对目标读者是常识），解释的篇幅留给真正陌生的东西：中文版里的新概念，英文版里的中国产品和说法。
- 出处缩成括号里的几个字（"（Epoch AI）"），完整链接放文末参考；论文是否在评审、作者利益关系这类限定，一句话带过，不展开成一段。

### 推断怎么标

正文里推断很多时，不要每段都写"以下是推断"，读起来生硬。在引子里声明一次（"讲已经发生的事都有出处；讲以后会怎样的地方是我的判断，会写明"），正文用"我的判断是""我的解释是"，整节都是推断的在节首说一句。英文版对应 "My read"。两种语言的标注数量要对得上。

## 配图

图是 X 上传播最多的部分：发布帖、摘录帖、别人的转发，常常只带一张图。所以每张图都按"单独被转发"的标准来评估。

- **一眼能懂。** 一张图只讲一个核心信息，标题就写这个信息（结论，不是话题）。读者扫三秒能说出这张图在讲什么。
- **字少、字大。** 多数人在手机上读 X，图会被缩到 360–400px 左右宽。一张 1600px 宽的图缩到约四分之一，30px 的字只剩 7px。审图时打开 SVG 看字号，按缩放后的大小判断能不能读；看不清就删字，宁可少说一点。
- **离开正文也看得懂。** 不用正文里才解释的简称，图里的词和正文完全一致（见"可读性"第 2 条）。
- **帮读者理解，不是装饰。** 用图来讲文字难讲的东西：关系、流程、对比、变化。只是把正文的一段话放进方框，不算一张好图。
- **并列选项的图要画出差别。** 几个方案并排时，图上要看得出它们在哪个维度上不同，不是几个名字排成一排。
- 流程用编号步骤，分类用"名称：一句话定义，加一个例子"，对照、取舍、选型用表格。
- 每篇要有封面图（X 长文的封面）和分享卡片图（站点的 og 图，做法见 `CLAUDE.md`），没有就在审稿里提出来。
- 插图如果是脚本生成的（`scripts/figures/<slug>.py`），改图时改脚本再重新生成，不要手改 SVG。

### 做图的具体规格

这些是 04-user-profile 那篇反复修改后定下来的，`scripts/figures/user-profile.py` 是现成的样板，新文章可以照着改：

- **画布 16:9（1600×900）。** 标题 56px（太长时自动缩小到一行放下），正文不小于 26px，页脚 22px。旧的 1600 宽、15–19px 字、2.3:1 的扁图在手机上看不清，已经弃用。
- **一张图的字控制在几十个字。** 每张图要有一个视觉锚点：图标、一个大数字、或一组一眼能比的条形/方块。只有文字框的图删掉，把内容放回正文。
- **页脚写"图 n · 出处"**，右侧写文章标题，单独转发时读者知道来源。
- **数据图：** 对比用两三根粗条加大号数字；"87 家里有 73 家"这类计数用方块图（waffle）；时间前后用浅色 / 深色同一色相。
- **几个并列的东西，画出具体差在哪里。** 例如三种广告位置，画成三个手机界面，标明"回答下面挂一条广告 / 推荐里插一条广告 / 不放广告，成交后抽成"，不要起三个抽象名字。
- **每方一个固定颜色**，全篇所有图一致。
- **中英文字放在同一个脚本里**（`t(zh, en)`），图号、文件名两边一致。英文通常比中文长，脚本要有按宽度自动缩小和换行的工具，生成后逐张看。
- **每次生成后，用 headless Chrome 渲染成 PNG 逐张看**，查文字溢出、重叠、出框。只看 SVG 源码发现不了这些问题。
- **大改图的方向前，先做一两张新旧对比的样稿给用户看**，确认方向再全部重画。
- **删掉或简化一张图时，图里独有的事实和数字要补回正文**，别让依据跟着图一起消失。
- **封面（5:2，1792×716）和分享卡片（1200×630）也由同一个脚本生成。** 站点两种语言共用一张分享卡片，站点主网址是英文，所以最终要用英文生成。发到 X 的图要导出成 PNG（2 倍清晰度）。

## 不写什么

这些写法会换来一时的流量，但伤信誉，而且在 X 的排序里本来也是亏的（负面反馈扣分很重）：

- 标题党开头：RIP、WTF、"所有人都错了"、"99% 的人不知道"。
- 诱导互动："转发 + 关注 + 回复关键词领资料"。
- 绝对化断言："任何目标都能实现""这是唯一的办法"。技术读者会去找反例。
- 没有出处的数字、"据说"、把推断写成事实。
- 复述别人已经讲透的观点。
- 套话："在当今快速发展的……""颠覆""赋能""一文读懂"。
- 为了显得专业而堆术语、自创术语。读者不懂的词每多一个，就多一个人关掉页面。

## 检查清单

审稿和自查都按这张表过，可读性优先。

**选题和角度**

1. 这篇的结论和已有的好文章有什么不同？有没有在复述别人的观点？
2. 讲的是结构性变化，还是只罗列现象？有没有从变化推到商业化或对读者的影响？
3. 决定结论的变量是织在主线里，还是另起了一节？
4. 每个具体案例是不是最新状态？过时的有没有改讲趋势？

**可读性**

5. 只读标题和第一屏，能不能说出全文结论？结论前面有没有典故、引语、背景或参考清单挡着？
6. 有没有自创的词、读者不会这样说的句子？
7. 每个关键概念是不是全文（含小标题、图、图注）只用一个词？
8. 随便挑一句话、一个小标题、一个图标题、一个方案名，单独拿出来能不能看懂？
9. 每个术语第一次出现时，有没有一句话定义？定义里有没有新的没解释过的术语？
10. 有没有一段话要读者同时记住三个以上的东西？能不能改通俗或画成图？
11. 每个抽象说法后面有没有具体例子？类比讲完有没有回到真实机制？
12. 转折处有没有路标？最关键的那句话有没有单独成段？

**结构和依据**

13. 每个小标题是不是一个论点？每节是不是只做一件事？
14. 并列的选项有没有写清具体差在哪里？
15. 有没有一样读者会收藏的、能直接拿去用的东西？
16. 有没有前后矛盾？数字、事实是否都有出处，推断是否标明？有没有"不写什么"里的任何一项？特别查三类：
    - 数字的口径：62% 是"用 AI 帮忙购物的人里"的 62%，不是"所有人"；
    - 前后的数量：开头说"看三件事"，后面图上是"两个变量"；
    - 论证里的变量：说"要看办一件事花多少钱"，后文却按"token 便宜所以一切便宜"往下推。
17. 结尾有没有把全篇串起来，而不是重抄开头？

**配图**

18. 每张图是不是一眼能懂、只讲一个信息、标题就是结论？
19. 缩到手机宽度后字还看得清吗？离开正文看得懂吗？
20. 有没有封面图和分享卡片图？

最后一问：让一个相邻领域的工程师读，哪一段他最可能读不下去？把那一段重写。
